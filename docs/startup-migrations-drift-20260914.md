# انحراف المخطط: ما يبنيه الإقلاع لا الـmigrations — 2026-09-14

تقرير فحص فقط. **لم أصلح الانحراف القديم** ولن أبدأ إصلاحاً واسعاً بدون طلبك. الملف موجود لأن اختبار التكامل كشف الحقيقة، ولأن لها أثراً على متجر جديد وعلى الاسترجاع من نسخة احتياطية.

## ما اكتشفه اختبار التكامل

قاعدة نظيفة + `prisma migrate deploy` **لا تكفي** لتشغيل المشروع: أول كتابة على `customers` تفشل بـ

```
The column `customers.is_both` does not exist in the current database
```

لأن هذا العمود — وغيره — لا يُنشأ في أي ملف migration، بل عند إقلاع السيرفر.

## أين يسكن هذا الكود الآن

كان داخل `src/server.ts`، فكانت الطريقة الوحيدة للحصول على قاعدة بشكل الإنتاج هي **تشغيل سيرفر HTTP**. نُقل كما هو إلى:

```
inventory-backend/src/config/startup-migrations.ts
```

- **21** عبارة `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`
- **5** عبارات `CREATE TABLE IF NOT EXISTS`
- كل عبارة مغلّفة بـ`try/catch` فلا يمنع فشل واحدة إقلاع السيرفر.
- النقل حرفي: عددا العبارات قبل وبعد متطابقان، و`server.ts` ما بقي فيه أي `ADD COLUMN`.
- مستدعاة من مكانين فقط: `server.ts` عند الإقلاع، واختبار التكامل على قاعدته المؤقتة.
- **تشغيل واحد مضمون:** الدالة تحفظ وعدها (`inFlight`)، فمن يستدعيها ثانياً ينتظر نفس التشغيل ولا يبدأ ثانياً. بدون هذا، نداءان متزامنان يتنافسان على قفل `ACCESS EXCLUSIVE` لكل عبارة.

## لماذا هي خارج الـmigrations النظامية؟

ليست غلطة واحدة بل نمط تراكم:

1. **ميزات نُشرت بسرعة على Railway** حيث الـmigrations تُطبّق تلقائياً، فأُضيف DDL «شبكة أمان» ليعمل النشر حتى لو لم تُطبّق migration.
2. **migration فاشلة سابقاً** في بيئة التطوير (مذكورة بذاكرة المشروع) جعلت الاعتماد على `ADD COLUMN IF NOT EXISTS` أسهل من إصلاح تاريخ الـmigrations.
3. **بعض العبارات تصحيحية**: أعمدة يتوقعها Prisma client وما كانت موجودة بقاعدة قديمة، فالإقلاع «يداويها» بدل تعديل تاريخ migrations منشور فعلاً.

النتيجة: `prisma migrate diff` يُظهر انحرافاً دائماً بين مجلد الـmigrations و`schema.prisma`، وهذا الانحراف **سابق لهذا العمل بالكامل** ولا يشمل أي كائن من كائناته (تحققت: لا `sales_agent_*` ولا `latitude/longitude` ولا `pending_approvals.customer_id` بقائمة الانحراف).

## الخطورة الحقيقية

| الحالة | الأثر |
|---|---|
| **متجر جديد (tenant جديد)** | قاعدة فارغة + `migrate deploy` = قاعدة **غير صالحة للعمل** حتى يُقلع السيرفر مرة. إذا أقلع السيرفر وفشلت إحدى العبارات (صلاحيات، قفل، نوع موجود) فالفشل **صامت** — سطر `warn` بالسجل فقط — والخطأ يظهر لاحقاً كـ«العمود غير موجود» عند أول عملية زبون. |
| **استرجاع من نسخة احتياطية** | `pg_restore` لنسخة حديثة يجيب الأعمدة معه، فالمشكلة لا تظهر. لكن استرجاع نسخة **قديمة** (قبل إضافة عمود) يحتاج إقلاع السيرفر مرة قبل أي عمل — وهذا غير موثّق بإجراء الاسترجاع. |
| **الإقلاع لا يُنتظر** | `server.ts` ينادي `void runStartupMigrations()` ثم `app.listen` مباشرة. فالطلبات تُستقبل **قبل** انتهاء الـDDL. النافذة أجزاء من الثانية، لكنها حقيقية: طلب يصل بتلك اللحظة على قاعدة تنقصها الأعمدة يفشل. هذا سلوك سابق لهذا العمل ولم أغيّره — تغييره يعني إما إقلاعاً أبطأ أو سيرفراً لا يقلع إذا تعلّقت عبارة DDL. |
| **بيئة اختبار/تكامل** | مُعالجة: اختبار التكامل ينادي نفس الدالة بعد `migrate deploy`. |

## الإصلاح الصحيح لاحقاً (لم يُنفّذ)

migration واحدة «تسوية» تحتوي نفس العبارات بصيغة `IF NOT EXISTS`، تُطبّق على كل قاعدة قائمة كـno-op، وتجعل قاعدة جديدة صالحة من `migrate deploy` وحده. بعدها يبقى `startup-migrations.ts` كشبكة أمان أو يُحذف. هذا تغيير يمسّ إقلاع كل متجر، فلا أبدأه بدون قرارك.

## توصية فورية بدون كود

أضف لإجراء «متجر جديد» وإجراء «الاسترجاع» سطراً واحداً: **بعد `migrate deploy` وقبل أي استخدام، أقلع السيرفر مرة وتحقق من سجل `[migration]`** — ثم اعمل. هذا يغطي الخطر الفعلي اليوم بلا أي مخاطرة.
